# 0009. 日次集約をGo側で行い、アプリ優先度で重複排除する

- ステータス: 採用
- 日付: 2026-09-03

## コンテキスト

同じ実測を複数のアプリが Health Connect へ書いており、`daily: [sum]` の列が多重計上されていた。2026-09-01 は歩数を3アプリが書いて 22,463歩（実際は約7,600歩）、消費カロリーは2アプリで基礎代謝の3.5倍だった。

ADR 0004 の汎用レコード設計は重複の概念を持たず、SQL の `GROUP BY` に集計関数を並べる日次集約では「上位アプリが覆う時間帯を除く」を表現できない。

あわせて、睡眠が開始時刻の日に帰属するため、日付が変わってから寝た日に前夜ぶんと当夜ぶんが合算されていた（20日ぶん、最大14.8時間）。

## 決定

**どのアプリを優先するかは端末の設定を正とする。** エクスポートDBの `health_data_category_priority_table` に「データソースと優先度」がそのまま入っており、これを読んで累積DBへ保存する。優先度はカテゴリ単位のため、種別の属するカテゴリを `config.yaml` の `category` に書く。重複排除は `dedupe: true` の種別だけに効かせる。

採用の単位は**アプリ × 現地日**。優先度の高いアプリがその日に記録していた時間帯（最初から最後のレコードまで）を覆ったものとし、下位アプリのレコードはその範囲と重なる割合だけ合計から外す。レコード単位で覆うと、歩いた区間しかレコードが無い歩数のような種別で隙間が空き、そこへ同じ実測が入り込む。

日付の帰属は `date_basis`（`start` / `end`）で選ぶ。睡眠は `end`（起床日）にする。

これらは SQL では書きにくいため、日次集約を Go 側へ移す。実物のエクスポートで検証したところ、消費カロリーの基礎代謝比の最大は 4.48 から 1.42、歩数は 22,463 から 7,596（優先アプリの実測 7,576）になった。

## 結果

- 良い影響: 端末の設定を変えれば出力も追随し、優先アプリを二重に管理しなくて済む。
- 悪い影響: 集約が全レコードをメモリへ読む（歩数で約11万件）。上位アプリが早朝と深夜にだけ記録した日は、間の時間帯の下位アプリのぶんまで落ちる。優先度が読めないエクスポートでは重複排除を行わない（消すより多いまま出す方が気付けるため）。
- 過去ぶんの `sum` 列は次の取り込みで値が下がり、睡眠は1日ずれる。

## 検討した代替案

- **採用するアプリを `config.yaml` に手で書く**: 実装は最も単純。却下: 端末の設定と二重管理になり、アプリを増やすたびに設定漏れで多重計上へ戻る。
- **時間帯が重なるレコードをアプリを問わずマージする**: 設定不要。却下: 重なった区間でどちらの値を採るかの判断が別途要る。既にある答え（優先度）を使わない理由が無い。
- **その日に記録があるアプリのうち最上位だけを丸ごと採る**: 実装が単純で値も正確。却下: 途中から使い始めた日（Fitbit が 15:45 から書き始めた 2026-08-23）で、それ以前の時間帯が丸ごと欠ける。
- **`sum` 列をやめて生データタブだけを正とする**: 却下: 読む側が毎回重複排除を実装することになる。

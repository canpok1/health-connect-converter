# 0004. 種別を汎用レコードで扱い、累積DBのスキーマをconfig.yamlから生成する

- ステータス: 採用
- 日付: 2026-08-29

## コンテキスト

`docs/draft/spec.md` は「種別の追加はエントリ1つ。コード変更は不要」を要件に挙げる一方、データモデルでは「種別ごとにテーブルを分ける（列が異なるため）」としている。対象は10〜15種別。

実物のエクスポートDBを調べた結果（`docs/health-connect-export-schema.md`）、種別テーブルは時刻の持ち方で instant / interval / series の3類型に収まり、それ以外の差は「値列の名前」と「単位の倍率」だけだと分かった。種別ごとの構造の違いは、設定で表せる範囲に収まっている。

一方で種別ごとの Go 構造体（`BloodPressure`・`HeartRate` …）を定義すると、種別を1つ足すたびに 構造体・読み出し・UPSERT・集約・出力 の5箇所へコードを追加することになり、要件と噛み合わない。

## 決定

種別固有の Go 型を作らず、全種別を1つの汎用レコードで表現する。

```go
type Record struct {
    UUID       string
    StartTime  int64              // UTC epoch ms
    EndTime    int64              // UTC epoch ms
    ZoneOffset int32              // 秒
    AppID      string
    Values     map[string]float64 // 種別固有の数値列
}
```

種別ごとの差は `config.yaml` が持つ。`time_layout`（3類型）が時刻列の読み方を、`columns` が値列の名前と単位倍率を決める。累積SQLiteのテーブルは `columns` から `CREATE TABLE IF NOT EXISTS` を組み立てて生成し、列の追加は `PRAGMA table_info` の差分から `ALTER TABLE ADD COLUMN` で行う（削除・型変更はしない）。日次集約の列も `daily` の関数リストから機械的に決まる。

種別を足す操作は `config.yaml` へのエントリ追加のみになる。

## 結果

- 良い影響: 種別追加がコード変更ゼロになる。3類型ぶんの読み出しを書けば、残り10種別以上が設定だけで足せる。store・集約・出力・配線を読み出しと独立に実装でき、複数人が並行して着手できる。
- 悪い影響: 値がすべて `float64` になり、`measurement_location` のような文字列列は表現できない（必要になった時点で拡張が要る）。列名や倍率の誤りがコンパイルではなく実行時エラーになるため、設定の検証を実装側で持つ必要がある。SQL を文字列で組み立てるので、識別子の検証（`^[a-z][a-z0-9_]*$`）を怠るとインジェクションの余地が生まれる。

## 検討した代替案

- 種別ごとの Go 構造体とテーブル定義: 型安全で、列ごとの単位や意味をコードに書ける。却下: 種別追加のたびに5箇所へ手を入れることになり、spec の要件に反する。
- 時刻列名も設定に書かせる（`time_layout` を持たない案）: 3類型という分類を実装に持ち込まずに済む。却下: 実物では類型ごとに列名が完全に一貫しており、種別ごとに5列ぶん書かせるのは誤記の余地を増やすだけになる。
- 全種別を1テーブルへ縦持ち（`type_key, value_name, value`）: 設定駆動にでき、列追加という概念自体が消える。却下: 日次集約と生データ出力で毎回ピボットが必要になり、SQL が複雑化する。spec の「種別ごとにテーブルを分ける」からも離れる。

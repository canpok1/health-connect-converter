# 0008. エクスポートに含まれる日は累積DBを日ごと置き換える

- ステータス: 採用
- 日付: 2026-09-03

## コンテキスト

累積DBはレコードを UUID をキーに追加・上書きするだけで、端末側で削除されたレコードを消さなかった。

Google Fit は細かいレコードを後から1日ぶんの合計1件へ書き換える。書き換えは新しい UUID のレコードとして現れるため、古い版が累積DBに残り、同じ実測が二重に数えられる。2026-09-02 のエクスポートと累積DBを突き合わせた実測は次のとおり。

| | エクスポートDB | 累積DB |
|---|---|---|
| 消費カロリーの総件数 | 11,758 | 12,083 |
| 2026-08-30 の Google Fit ぶん | 1,773.7kcal（45件） | 3,327.6kcal（62件） |
| 運動セッションの総件数 | 194 | 233 |

累積DBはエクスポートより長い履歴を持つのが目的（血圧は2019年から。エクスポートは2024-02以降しか持たない種別がある）なので、単純に全件を入れ替えることはできない。

## 決定

取り込んだレコードが属する**現地日**を集合として取り、その日ぶんの既存レコードを削除してから挿入する。エクスポートに現れない日は触らない。

エクスポートはその日の最新状態なので、同じ日について累積DB側が持つ「エクスポートに無いレコード」は端末から消えたものと判断できる。日単位にすることで、エクスポートが覆っていない過去は保持される。

## 結果

- 良い影響: 端末側の削除・作り直しに追随する。ADR 0004 の「configに列を足すだけ」という性質は保ったまま、合計が実態と合う。
- 悪い影響: 削除は現地日を計算する SQL 式で行うため索引が効かず、種別ごとに全表走査になる（取り込みは1時間に1回で実害は無い）。エクスポートが一時的に欠けた日を取り込むと、その日の既存レコードが失われる。
- 既存の累積DBに溜まった残骸は、その日が次のエクスポートに含まれた時点で消える。含まれない日（エクスポートの保持期間より古い日）には残る。

## 検討した代替案

- **毎回すべて削除して入れ替える**: 実装が最も単純。却下: エクスポートが持たない古い履歴（2019年からの血圧など）を失う。累積DBを置く意味が無くなる。
- **レコード単位で消えたものを検出する**: 端末側に無い UUID を消す。却下: 「エクスポートに無い」が削除を意味するのか、単にエクスポートの範囲外なのかを区別できない。
- **書き換え前後を突き合わせて古い版だけ消す**: 精度は高い。却下: Health Connect 側の書き換え規則に依存し、規則が変わると静かに壊れる。

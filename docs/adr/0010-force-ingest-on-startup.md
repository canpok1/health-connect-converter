# 0010. 起動後の最初の1周は新着ZIPの有無によらず取り込む

- ステータス: 採用
- 日付: 2026-09-12

## コンテキスト

取り込みは「エクスポートZIPの `modifiedTime` が前回処理分より新しいときだけ」行う設計だが、成立していなかった。state への保存が `time.RFC3339`（秒精度）で、Drive が返す `2026-09-11T16:30:56.853Z` のミリ秒が落ちる。復元値が常に実際より古いため、同じZIPを毎周回（1時間おき）再取得・再取り込みしていた。1周あたり20MBのダウンロードとSheets約40リクエストが恒常的に走る。

一方この壊れ方には副作用があり、`config.yaml` へ種別を追加した当日に出力へ反映された。厳密に直すと、累積DBに新種別のデータが無いため次のエクスポート（最大24時間後）まで出力に現れず、デプロイした変更をその場で確認できない。

## 決定

保存を `time.RFC3339Nano` にして「新着時のみ」を成立させたうえで、**プロセス起動後の最初の1周だけは新着の有無によらず最新ZIPを取り込む**。`--once` は毎回プロセスが起動するため常に取り込む。

Watchtower はイメージ更新時にコンテナを作り直すので、起動は設定変更・コード変更とほぼ同義になる。「変えたら次の1周で反映される」を、変更検知の仕組みを足さずに得る。

## 結果

- 良い影響: 定常状態の無駄がゼロになる。デプロイ直後に反映を確認できる。読み側の `time.Parse(time.RFC3339, ...)` はミリ秒付きも受けるため、既存 state の移行は不要。
- 悪い影響: OS再起動やクラッシュ後の再起動でも1回ぶん取り込みが走り、起動直後の1周は20MBのダウンロードが確定する。
- 取り込みが走ったことは「何かが変わった」を意味しなくなる。

## 検討した代替案

- **毎周回の再取り込みを仕様として追認する**: ドキュメント修正だけで済む。却下: バグ由来の挙動を仕様へ昇格させることになり、20MB/時のダウンロードとSheets 40リクエスト/時が恒常的に残る。
- **`config.yaml` の内容ハッシュを state に持ち、変化時に再取り込みする**: 意図が明示的になる。却下: コード側の集計ロジック変更は検知できず、ハッシュ計算と再取り込み経路の実装が増える。起動時1回でほぼ同じ効果が得られる。
- **新着時のみに厳格化する（spec の記述どおり）**: 無駄はゼロ。却下: 設定・コードの変更が次のエクスポートまで反映されず、最大24時間後まで検証できない。

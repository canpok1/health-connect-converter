# 0011. 睡眠ステージはステージ自身の時刻で取り込み、日付を決める時刻を別に持つ

- ステータス: 採用
- 日付: 2026-09-12

## コンテキスト

2026-09-09 に Fitbit が接続され `sleep_stages_table` にデータが入った（覚醒/浅い/深い/REM）。`docs/draft/spec.md` が当初ほしがっていた `sleep_deep_min` を出せる。

子テーブルの形は既存の series 型（`parent_key` + 値列 + `epoch_millis`）と違い、`stage_start_time` / `stage_end_time` / `stage_type` を持つ。値は数値ではなく種別で、集計は「種別ごとの合計時間」になる。

日次集計の日付は `date_basis` で「レコード自身の開始か終了か」しか選べない。ステージ自身の時刻をそのまま使うと、日付をまたぐひと晩が2日に割れ、`end`（起床日）で数えている `sleep` と食い違う。

## 決定

子テーブルを扱う `time_layout: segment` を足す。子テーブル名・開始/終了/種別の列名・`stage_type` から値名への対応表を `config.yaml` に書き、コード変更なしで種別を増やせる形（[ADR 0004](0004-config-driven-generic-records.md)）を保つ。

**1ステージ＝1レコードとし、レコードの開始・終了にはステージ自身の時刻を入れる。** そのうえで、日次集計の日付を決めるためだけの時刻をレコードへ別項目として持たせ、親セッションの終了時刻（起床時刻）を入れる。累積DBにもこの項目の列を足す。対応表に無い `stage_type` はレコードごと捨てる。

## 結果

- 良い影響: 生データタブにひと晩の推移がそのまま並び、行の順序が時刻で確定する。日次集計は `sleep` と同じ起床日に寄る。
- 悪い影響: モデルと累積DBに固定の項目が1つ増える。**既存テーブルへ列を足す経路も要る**（今は設定に書いた値の列しか後から追加できない）。既存レコードはこの項目が空のままで、従来どおり `date_basis` で日付が決まる。
- 捨てた `stage_type` は出力に現れない。日次の件数と、合計分と `sleep_duration_min_sum` の差で気付ける。

## 検討した代替案

- **レコードの開始・終了に親セッションの期間を入れる**（当初の決定。指摘を受けて反転した）: 固定項目の追加が要らず最も安い。却下: ひと晩ぶんのレコードが全て同じ時刻になり、生データタブの1行が単体では意味を持たない。並び順も `ORDER BY start_time` が同値で決まらず保証がない。ステージの開始時刻はレコードの一意キーに埋め込まれるが、生データタブに一意キーは出力されないため辿れない。
- **ひと晩を1レコードにまとめる**（種別ごとの合計だけ持つ）: 順序の問題が起きず実装も安い。却下: ステージの推移が完全に失われ、生データタブの中身が `daily_summary` の列とほぼ重複する。
- **睡眠専用の実装にする**: 汎用化の分岐が要らない。却下: ADR 0004 の「種別の追加は設定1エントリ、コード変更は不要」に反する。

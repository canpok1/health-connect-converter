# 0011. 睡眠ステージはステージ自身の時刻で持ち、起床日に数える

- ステータス: 採用
- 日付: 2026-09-12

## コンテキスト

2026-09-09 に Fitbit が接続され `sleep_stages_table` にデータが入った（覚醒/浅い/深い/REM）。`docs/draft/spec.md` が当初ほしがっていた `sleep_deep_min` を出せる。

ステージは親の睡眠セッションにぶら下がる区間で、ひと晩に何十件も並ぶ（2026-09-10 の夜は86件）。日次集計の日付は「レコード自身の開始か終了か」で決めているため、ステージ自身の時刻をそのまま使うと、日付をまたぐひと晩が2日に割れ、起床日で数えている睡眠時間と食い違う。

## 決定

睡眠ステージを1つの種別として扱い、**1ステージ＝1レコードとして、ステージ自身の開始・終了を持たせる。** 実測データとしては、これに加えて親セッションの終了時刻（起床時刻）とステージ種別を持つ。

集計モデルへ変換するときに、**現地日は親セッションの終了時刻から決める**。長さはステージ種別ごとの値（`deep_min` など）へ振り分ける。この振り分けと日付の決め方は睡眠ステージの変換に閉じる（[ADR 0012](0012-split-measured-data-from-aggregation-model.md)）。

対応表に無い `stage_type` はレコードごと捨てる。ステージ種別の意味は AOSP の `SleepSessionRecord.java` で確認した（1=覚醒 / 4=浅い / 5=深い / 6=REM）。

## 結果

- 良い影響: 生データタブにひと晩の推移がそのまま並び、行の順序が時刻で確定する。日次集計は睡眠時間と同じ起床日に寄る。
- 悪い影響: 親セッションの終了時刻をステージ側にも持つため、同じ値がひと晩ぶん重複して入る。
- 捨てた `stage_type`（不明・ベッド外の覚醒など）は出力に現れない。日次の件数と、合計分と睡眠時間の差で気付ける。

## 検討した代替案

- **レコードの開始・終了に親セッションの期間を入れる**（当初の決定。指摘を受けて反転した）: 日付の決め方を変えずに済み最も安い。却下: ひと晩ぶんのレコードが全て同じ時刻になり、生データタブの1行が単体では意味を持たない。並び順も開始時刻が同値のため保証がない。ステージの開始時刻は一意キーに埋め込まれるが、生データタブに一意キーは出力されないため辿れない。
- **ひと晩を1レコードにまとめる**（種別ごとの合計だけ持つ）: 順序の問題が起きず実装も安い。却下: ステージの推移が完全に失われ、生データタブの中身が `daily_summary` の列とほぼ重複する。
- **共通のレコードに「どの日に数えるか」の欄を足す**: 変換を種別ごとに書かずに済む。却下: 血圧や体重の保存先にも同じ欄が増える。この問題が ADR 0012 の契機になった。

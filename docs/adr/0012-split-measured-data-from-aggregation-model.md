# 0012. 実測データと集計モデルを分け、種別ごとの型で表す

- ステータス: 採用
- 日付: 2026-09-12

## コンテキスト

[ADR 0004](0004-config-driven-generic-records.md) は全種別を1つの汎用レコードで表し、累積DBの列を `config.yaml` から生成する形にした。種別追加が設定1エントリで済む利点は効いており、HRV と呼吸数は設定の追記だけで足せた（PR #16）。

睡眠ステージで限界が出た。ステージは「区間の時刻」と「どの日に数えるか（起床日）」が食い違うため、日付を決める時刻をレコードへ持たせる必要がある。ところが汎用レコードに足すと、血圧や体重の保存先にも同じ欄が増える。**ある種別の都合が、無関係な種別の保存先を変えてしまう。**

原因は、汎用レコードが「実測データの表現」と「集計処理の入力」を兼ねていること。集計モデルは集計側の都合で決めたものなのに、それを保存しているため、集計の都合が保存の形へ漏れる。

## 決定

モデルを3層に分ける。種別ごとの実体は [docs/domain-model.md](../domain-model.md) に置く。

| 層 | 単位 | 保存 |
|---|---|---|
| 保存用のモデル | 種別ごと（親子を結合して畳み、アプリ名を引き、単位を直す） | **する** |
| 集計用のモデル | 共通（現地日・期間・記録元アプリ・値） | しない |
| サマリーモデル | 共通（日次の集計結果） | しない |

**エクスポートDBの表を写した型は作らない。** 結合結果をそのまま保存用へ読む。上流の形は [スキーマ調査](../health-connect-export-schema.md)が正本で、上流が変わったときの影響は種別ごとの読み出しに閉じる。

読み出しと変換は種別ごとに書き、種別固有の事情（睡眠ステージの起床日）は「保存用 → 集計用」の変換へ閉じる。`config.yaml` は廃止し、読み方も方針（窓・日次関数・重複排除）も種別ごとのコードへ移す。設定は既にイメージへ同梱され差し替えない（[ADR 0002](0002-bundle-config-into-image.md)）ため、変更にビルドが要る点は変わらない。

**やめるのは型の共通化であって、定型処理の共有ではない。** 類型ごとのSQL組み立て、重複排除、日次集計、タブ書き込みは共通の部品として残す。

## 結果

- 良い影響: 変更の理由が層ごとに分かれる。上流の表が変われば読み出しだけ、保存の都合なら保存用だけ、集計の都合なら集計用とサマリーだけが変わる。種別固有の事情を型で表せ、値がすべて `float64` という ADR 0004 の制約も外せる。
- 悪い影響: 種別追加が設定1エントリで済まなくなり、`docs/draft/spec.md` の当初要件を捨てる。種別ごとに型と読み出しと変換を書くため部品が増える。ADR 0004 を置き換え、ADR 0002 は対象を失う。
- 累積DBの中身は変えないため、移行中は新旧の出力が一致することで確かめられる。

## 検討した代替案

- **保存先の列だけ種別ごとに持たせる**（汎用レコードは残す）: 今回の結合は切れ、変更も小さい。却下: 実測と集計を1つの型が兼ねる構造が残るため、同じ種類の漏れが別の形で再発する。
- **上流の表を写した型も層として持つ**: 上流の形が型に現れる。却下: 単純な種別では保存用との差がアプリ名の解決と単位変換だけ。親子構造の種別は結合して読めばそのまま保存用の形になり、親と子の型を突き合わせるほうが遠回りになる。
- **現状維持（汎用レコードへ欄を足す）**: 最も安い。却下: 無関係な種別の保存先が変わる、という今回の問題がそのまま残る。

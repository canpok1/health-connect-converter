# 0012. 実測データと集計モデルを分け、種別ごとの型で表す

- ステータス: 採用
- 日付: 2026-09-12

## コンテキスト

[ADR 0004](0004-config-driven-generic-records.md) は全種別を1つの汎用レコードで表し、累積DBの列を `config.yaml` から生成する形にした。種別追加が設定1エントリで済む利点は実際に効いており、HRV と呼吸数は設定の追記だけで足せた（PR #16）。

睡眠ステージの取り込みで限界が出た。ステージは「区間の時刻」と「どの日に数えるか（起床日）」が食い違うため、日付を決める時刻をレコードへ持たせる必要がある。ところが汎用レコードにそれを足すと、血圧や体重の保存先にも同じ欄が増える。**ある種別の都合が、無関係な種別の保存先を変えてしまう。**

原因は、汎用レコードが「実測データの表現」と「集計処理の入力」を兼ねていること。集計モデルは集計側の都合で決めたものなのに、それをそのまま保存しているため、集計の都合が保存の形へ漏れる。

## 決定

モデルを4層に分ける。種別ごとの実体は [docs/domain-model.md](../domain-model.md) に置く。

| 層 | 単位 | 保存 |
|---|---|---|
| ヘルスコネクトのモデル | 種別ごと（上流の表の写し。判断を持たせない） | しない |
| 保存用のモデル | 種別ごと（親子を畳み、アプリ名を引き、単位を直す） | **する** |
| 集計用のモデル | 共通（現地日・期間・記録元アプリ・値） | しない |
| サマリーモデル | 共通（日次の集計結果） | しない |

変換は種別ごとに書き、種別固有の事情（睡眠ステージなら起床日の決め方）は「保存用 → 集計用」の変換へ閉じる。`config.yaml` は廃止し、読み方も方針（生データの窓・日次関数・重複排除）も種別ごとのコードへ移す。設定は既にイメージへ同梱され環境ごとに差し替えない（[ADR 0002](0002-bundle-config-into-image.md)）ため、変更にビルドが要る点は変わらない。

**やめるのは「種別の型の共通化」であって、定型処理の共有ではない。** 時刻の持ち方の類型ごとのSQL組み立て、重複排除、日次集計、タブ書き込みは共通の部品として残す。

## 結果

- 良い影響: 変更の理由が層ごとに分かれる。上流の表が変われば写しの層だけ、保存の都合なら保存用だけ、集計の都合なら集計用とサマリーだけが変わる。種別固有の事情を型で表せ、値がすべて `float64` という ADR 0004 の制約も外せる。
- 悪い影響: 種別追加が設定1エントリで済まなくなり、`docs/draft/spec.md` の当初要件を捨てる。種別ごとに型2つと変換2つを書くため部品が増える（写しの層は機械的に薄く保って抑える）。ADR 0004 を置き換え、ADR 0002 は対象を失う。
- 累積DBの中身は変えないため、移行中は新旧の出力が一致することで確かめられる。

## 検討した代替案

- **保存先の列だけ種別ごとに持たせる**（汎用レコードは残す）: 今回の結合は切れ、変更も小さい。却下: 実測と集計を1つの型が兼ねる構造が残るため、同じ種類の漏れが別の形で再発する。
- **実測データを1層にする**（写しと保存用を分けない）: 部品が減る。却下: 心拍・速度・睡眠ステージは上流が親子2表なのに保存したい形は1行1件で、構造が違う。分けないと写しの都合と保存の都合が同じ型に同居する。
- **現状維持（汎用レコードへ欄を足す）**: 最も安い。却下: 無関係な種別の保存先が変わる、という今回の問題がそのまま残る。

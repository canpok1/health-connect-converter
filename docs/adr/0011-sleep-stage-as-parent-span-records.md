# 0011. 睡眠ステージは親セッションの期間を持つレコードとして取り込む

- ステータス: 採用
- 日付: 2026-09-12

## コンテキスト

2026-09-09 に Fitbit が接続され `sleep_stages_table` にデータが入った（覚醒/浅い/深い/REM）。`docs/draft/spec.md` が当初ほしがっていた `sleep_deep_min` を出せる。

子テーブルの形は既存の series 型（`parent_key` + 値列 + `epoch_millis`）と違い、`stage_start_time` / `stage_end_time` / `stage_type` を持つ。値は数値ではなく種別で、集計は「種別ごとの合計時間」になる。

日次集計の日付は `date_basis` で「レコード自身の開始か終了か」しか選べない。ステージ自身の時刻で数えると、日付をまたぐ一晩が2日に割れ、`end`（起床日）で数えている `sleep` と食い違う。

## 決定

子テーブルを扱う `time_layout: segment` を足す。子テーブル名・開始/終了/種別の列名・`stage_type` から値名への対応表を `config.yaml` に書き、コード変更なしで種別を増やせる形（[ADR 0004](0004-config-driven-generic-records.md)）を保つ。

**1ステージ＝1レコードとし、レコードの開始・終了には親セッションの開始・終了を入れる。** ステージの長さは値の列（`deep_min` など）で持つ。これで `date_basis: end` がそのまま効き、累積DBのスキーマもモデルも変えずに済む。対応表に無い `stage_type` はレコードごと捨てる。

## 結果

- 良い影響: 日次集計が `sleep` と同じ日（起床日）に寄る。固定列の追加も既存テーブルのマイグレーションも要らない。
- 悪い影響: 生データタブからステージの時刻が失われる。一晩の内訳は分かるが、深い睡眠が前半に寄っていたかは見られない。後から時刻を持たせるにはモデルと累積DBへ項目の追加が要る。
- 捨てた `stage_type` は出力に現れない。日次の件数と、合計分と `sleep_duration_min_sum` の差で気付ける。

## 検討した代替案

- **ステージ自身の時刻を持ち、日付決定用の時刻をモデルと累積DBへ追加する**: 生データが正確になる。却下: 固定列の追加と既存テーブルのマイグレーションが要るのに対し、得られるのは生データの深掘りだけ。必要になった時点で足せる。
- **睡眠専用の実装にする**: 汎用化の分岐が要らない。却下: ADR 0004 の「種別の追加は設定1エントリ、コード変更は不要」に反する。
- **ステージ自身の時刻のまま `date_basis: end` で数える**: 実装は最小。却下: 日付をまたぐ一晩が2日に割れ、`sleep` の日付と食い違う。
